# ADR 0001: Database Credential Lifecycle

- Status: accepted for lab bootstrap; production hardening remains
- Date: 2026-08-24

## Context

Terraform must create an encrypted RDS database without placing a password in configuration, variable files, plans, state inputs, user data, logs, or Git. The application also needs a testable path to one authorized database credential.

## Decision

RDS generates and manages the initial master password in Secrets Manager. Terraform handles only the managed secret ARN. The EC2 role is limited to `DescribeSecret` and `GetSecretValue` for that exact secret plus `kms:Decrypt` through Secrets Manager for the database key. No operator or build command retrieves the secret value.

The secret ARN and private database endpoint may be passed to the instance as non-secret configuration. Secret retrieval occurs only at application runtime after the database integration code is introduced and tested.

## Consequences

- No database password is generated by Terraform or stored in Terraform inputs.
- RDS owns master-password generation and rotation.
- IAM and KMS access can be tested independently from broad AWS permissions.
- The current managed secret contains a privileged bootstrap credential. Before calling the application production-ready, create a separate least-privilege database user, give it only the required schema permissions, move the application to a separately rotated secret or IAM database authentication, and remove application-role access to the master secret.

The repository and interview narrative must not claim database least privilege is complete until that final migration and an authorization test have passed.
